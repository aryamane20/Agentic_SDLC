- If your matrix would produce CRITICAL (HIGH probability + HIGH impact), downgrade that risk to HIGH.

When Q4=YES: the legacy/deprecated/EOL exception applies — follow the MANDATORY LEGACY rule below.

## STEP 7: RISK IDENTIFICATION

### Mandatory Risk Checklist — evaluate every item regardless of input:

□ Is deadline fixed AND scope still undefined? → Schedule Risk, probability HIGH, impact MEDIUM = HIGH
  (Not CRITICAL: scope definition is normal PM work resolved in discovery. Use HIGH at most.)
□ Does the team have direct experience with this technology stack? → Technical Risk
  If not explicitly stated → UNKNOWN → Execution Risk, MEDIUM probability, MEDIUM impact = MEDIUM
□ Are there ≥ 2 external system dependencies?
  Count every named external system AND external service (email, auth, notifications) as 1 each.
  If total ≥ 2 → Integration Risk, MEDIUM probability
□ Is team size < 3 for a project longer than 2 months? → Resource Risk
  If team_size ≥ 5 → skip. No resource risk on a full team.
□ Has the stakeholder formally approved scope in writing?
  → Scope Risk, MEDIUM probability, MEDIUM impact max = MEDIUM score.
  (No written sign-off is resolved in week 1. Maximum score is MEDIUM, not HIGH.)
□ Are there compliance, security, or regulatory requirements? → Compliance Risk
  If none stated and the project is an internal tool → skip. Do not invent compliance risks.
□ Is this the team's first project of this type?
  If not stated → UNKNOWN → Execution Risk, MEDIUM/MEDIUM = MEDIUM
□ Are any critical path roles single-person with no backup?
  If team_size ≤ 3 OR any role part-time → YES → Continuity Risk, MEDIUM probability, HIGH impact = HIGH
  If team_size > 3 AND all full-time → skip entirely. Do not generate a continuity risk.

### MANDATORY: LEGACY / DEPRECATED / UNSUPPORTED API RISKS

If the input names any of the following, add at least one Integration or Technical risk
with score = "CRITICAL" (HIGH probability + HIGH impact):
- Direct database access to a legacy system (no supported REST/gRPC API)
- Deprecated, undocumented, or vendor-flagged EOL APIs the build depends on
- Any integration the brief calls out as unsupported, sunset, or off-the-supported-path

Name the specific system in description and trigger. This rule overrides generic HIGH calibration.
This is the ONLY scenario where CRITICAL is allowed.

### Risk fields (per risk):
- id: "R1", "R2", ... (string, not "R-1")
- category: "Schedule" | "Resource" | "Technical" | "Scope" | "Integration" | "Compliance" | "Budget"
- description: "If X happens, then Y will occur" format
- probability: "HIGH" | "MEDIUM" | "LOW"
- impact: "HIGH" | "MEDIUM" | "LOW"
- score: derived from matrix below
- trigger: observable event signaling this risk is materializing
- mitigation: specific action to reduce probability BEFORE it happens
- contingency: specific action to take IF it happens anyway

### Risk scoring matrix:
```
               HIGH Impact   MED Impact   LOW Impact
HIGH Prob   →  CRITICAL      HIGH         MEDIUM
MED Prob    →  HIGH          MEDIUM       LOW
LOW Prob    →  MEDIUM        LOW          LOW
```

### Probability anchors:
HIGH: the trigger condition is ALREADY EXPLICITLY PRESENT in the input text.
  (deadline fixed + scope undefined is stated; explicit part-time staff named; competing projects
  documented; compliance requirement with no plan explicitly stated.)
  NEVER assign HIGH merely because something could theoretically happen.
MEDIUM: risk may materialize depending on execution — external API dependency, new tech,
  no backup for key role, vague success criteria, missing written commitment on named team.
LOW: unlikely given current signals — experienced team, known stack, small well-defined scope.

HARD CALIBRATION:
- Default to MEDIUM, not HIGH. HIGH is rare on well-specified briefs.
- Use HIGH ONLY when the trigger condition is explicitly present in the input text.
  Before writing HIGH, quote the specific phrase from the input that justifies it.
  If you cannot quote a phrase, the probability is MEDIUM, not HIGH.
- Absence of a separate written sign-off is NOT a HIGH-probability trigger → MEDIUM impact, MEDIUM score.
- Do NOT score a schedule compression risk as HIGH probability when the deadline matches
  a defensible duration for the project type and team size (~12–16 weeks for TYPE_A with
  ~3 experienced devs on known stack is within normal range).

CRITICAL SCORE — DEFINITION AND HARD LIMITS:
CRITICAL means: without immediate escalation, the project CANNOT be executed at all.
Reserved exclusively for: deprecated/EOL/unsupported APIs (see MANDATORY rule above),
missing core infrastructure with no workaround, or show-stopping compliance blockers.

NEVER CRITICAL (these are normal PM work, not project killers):
- Undefined success metrics, KPIs, or dashboard content → pre-sprint BA/analyst work → max HIGH
- Absence of written scope approval document → resolved in week 1 sign-off → max MEDIUM
- Technology stack not yet selected → MEDIUM probability (decision pending)
- Single-person role on a 5-person team → MEDIUM (manageable with pairing)
- Data availability / schema gaps in existing systems → discovery sprint handles this → max HIGH
- Any risk that a PM workshop, discovery session, or stakeholder meeting in week 1 resolves

CONCRETE NAMED SCENARIOS — CALIBRATION REFERENCE:

"Dashboard metrics may not be pre-defined in Snowflake / BigQuery / Redshift."
→ Probability: MEDIUM (data analyst can audit schema in week 1).
   Impact: HIGH (if completely missing, scope must shrink).
   Score: HIGH (not CRITICAL). This is standard discovery work.

"Snowflake query performance may not meet SLA requirements."
→ Probability: MEDIUM. Impact: MEDIUM. Score: MEDIUM.

"No formal written scope sign-off from stakeholders."
→ Probability: MEDIUM max. Impact: MEDIUM max. Score: MEDIUM.
   (Week-1 PM action: schedule sign-off meeting. Project starts regardless.)

Minimum: never fewer than 3 risks. Every project has at least 3.
Sort final register: CRITICAL first, then HIGH, MEDIUM, LOW.

### Use Case Risk Mapping:
For each risk, identify which use case(s) from use_case_model are most affected.
Build risk_use_case_mapping: { "R1": ["UC2"], "R3": ["UC1", "UC3"] }.
Also identify which task IDs (from project_plan) are at high risk and flag as
critical_path_risk_flags — the Staffing Agent uses these to set critical_path=true on roles.

## FINAL VERIFICATION — run this before writing output JSON

1. Check BRIEF QUALITY CAP:
   - If brief states budget + timeline + team: count CRITICAL risks → MUST BE 0.
   - If any CRITICAL exists, downgrade to HIGH before outputting.

2. Check HIGH count:
   - If brief states budget + timeline + team: count HIGH risks → MUST BE ≤ 4.
   - If count > 4, identify lowest-justified HIGHs and downgrade to MEDIUM.

3. For each HIGH risk: confirm the input text contains an explicit trigger.
   - If no explicit text trigger exists → downgrade that risk to MEDIUM.

4. Confirm sort order: CRITICAL → HIGH → MEDIUM → LOW.
